**Incidental observation.** The upgrade happened while 4 `SecretSpec`s existed
(`default/fernet-key`, and `app-admin`, `deploy-key`, `shared-token` in
`secretspec-demo`): the owner was running a demo on the cluster in parallel,
created after the pre-check and before Flux rolled the new version out. The new
operator reconciled all of them as `UpToDate` at startup, with no value
changes. (A `shared-token` regeneration seen a few seconds later was the owner
editing that spec, `length: 48` → `64`, not an effect of the upgrade.) The
scenarios were postponed until the demo was finished and its SecretSpecs
deleted; the pre-checks were repeated (no `SecretSpec` and no Secret labelled
`app.kubernetes.io/managed-by=secretspec-operator` anywhere).

### RBAC (scenario h)

ServiceAccount `secretspec-system:secretspec-operator`; checked with
`kubectl auth can-i --as=system:serviceaccount:secretspec-system:secretspec-operator`.

| Question | Answer |
|---|---|
| `list secrets -A` | **yes** |
| `delete secrets -A` | **no** |
| `delete secrets -n test-secretspec` | no |
| `get leases` (unnamed) `-n secretspec-system` | no — see note |
| `get leases/secretspec-operator -n secretspec-system` | **yes** |
| `update leases/secretspec-operator -n secretspec-system` | yes |
| `get` / `update leases/other -n secretspec-system` | no / no |
| `get leases -n kube-system` | no |
| `create clusterroles` | **no** |

Note on the leases rule: the Role grants `get`/`update` on the Lease
`secretspec-operator` only (`resourceNames`), plus `create` on `leases` (a
create cannot be limited by name). An *unnamed* `can-i get leases` therefore
answers `no`; the question has to name the Lease. This is the intended scoping,
not a defect; a test script should ask for `leases/secretspec-operator`. The
ClusterRole grants Secrets `get,list,watch,create,patch,update` — no `delete`.

## Teardown

1. `kubectl delete namespace test-secretspec --wait` — gone (`NotFound`).
2. `kubectl get secrets -A -l app.kubernetes.io/managed-by=secretspec-operator` → `No resources found`; `kubectl get secretspecs -A` → `No resources found`.
3. The Flux deployment was left running at `0.1.2-rc.1` (HelmRelease Ready, pod `1/1`, 0 restarts); the CRD was not touched.

While the namespace was terminating, the operator logged 15 `WARN` lines
(`apply of Secret failed: 403 Forbidden`, `publishing event failed`, all at
the same second for the 7 specs). Kubernetes forbids creating objects in a
terminating namespace; the operator evidently tried to re-create Secrets that
the namespace deletion was removing. This is namespace-teardown noise, not seen outside the
teardown; no `ERROR` lines at all.

## Deviations and notes

- **Unnamed `can-i get leases` is `no`.** Correct for the `resourceNames`-scoped
  Role (see RBAC note); the test question must name the Lease.
- **`kubectl debug -i` with a command** prints an attach warning and falls
  back to streaming logs (see scenario j). `docs/operations.md` describes the
  interactive form (`-it`), which this test did not drive; the document is
  otherwise accurate (`--profile=restricted`, `--target=operator`,
  `/proc/1/root/`, `127.0.0.1:8080/healthz`).
- **`LowEntropy` Warning Event** on `garage` (`access-key-id`, 96 bits) from the
  example, as designed.
- **Retain adoption writes the Secret once** (`resourceVersion` moves, values
  unchanged).
- The HTTP chart repository was exercised by the Flux upgrade path; the OCI chart
  was exercised only through `cosign verify`.
- The documentation commands (`docs/installation.md` cosign commands,
  `docs/operations.md`) worked as written.
